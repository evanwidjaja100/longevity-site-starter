# Release Acceptance

Consumer Lab release acceptance additionally requires: three eligible synthetic reports sort deterministically; the blocked report remains unpublished; category counts match; no private test-record field appears publicly; structured rows escape markup; affiliate disclosure precedes approved seller links; the search dialog restores focus; the 320px layout has no page overflow; value sort remains hidden without complete governed value data; and schema mirrors the visible eligible list.

A production candidate is acceptable only when required automated checks pass; Docker bootstrap and smoke tests pass in a supported environment; no P0/P1 security finding is unresolved; representative high-risk and commercial articles are correctly blocked or allowed; roles cannot exceed intended capabilities; schema matches visible facts; accessibility has no known critical barrier; backup and rollback are verified; and editorial leadership approves public wording.

Advisory dependency findings, performance opportunities, and minor accessibility defects may be accepted only with a named owner, documented rationale, and due date. Missing real test evidence, incomplete medical review, fabricated data, secret exposure, or a broken restore path is always blocking.
## Production Readiness v2 acceptance additions

Acceptance also requires both dependency lockfiles, deterministic manifest parity, minimum and named critical-suite discovery, current immutable approvals, independent reviewer and test/commercial approvals, an allowlisted anonymous REST contract, valid packaged scoring configuration, complete freshness-cycle coverage, active append-only audit storage, semantic lifecycle dates, and privacy-safe contact retention/rate limiting.

Record each requirement as `implemented`, `tested locally`, `tested in CI`, `tested on staging`, `human verified`, or `external control unknown`. Only the applicable verified state is acceptable; code existence alone is not production evidence.
